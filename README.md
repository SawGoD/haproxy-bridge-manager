# HAProxy Bridge Manager

Локальный TUI-менеджер TCP-маршрутов HAProxy. Go, Bubble Tea, Bubbles и Lip Gloss; один бинарник `haproxy-bridge`, Linux amd64/arm64. Веб-интерфейса, Remnawave API и удалённого управления по SSH нет. TLS-тестирование не меняет режим проксирования: приложение не выполняет TLS-терминацию HAProxy.

**Статус: версия для испытаний.** Docker integration-тесты HAProxy 3.2 и терминальный smoke-тест на Ubuntu 24.04 выполнены. До продуктивного использования необходима приёмочная проверка через SSH на целевом сервере с его реальной конфигурацией. Разработка не изменяет `/opt/haproxy/haproxy.cfg` и не перезапускает продуктивный HAProxy.

## Сборка и установка

Требуется Go версии из `go.mod` и новее. Пользователю готового бинарника Go, Python и Node.js не нужны. Для управления Docker необходим Docker CLI, для Native — HAProxy и systemd.

```sh
make test
make build
make release
# На целевом Linux, выбрав правильную архитектуру:
sudo install -m 0755 dist/haproxy-bridge-linux-amd64 /usr/local/bin/haproxy-bridge
haproxy-bridge
```

`dist/SHA256SUMS` содержит контрольные суммы. Параметр `--version` выводит версию; `make release VERSION=0.1.0` задаёт её при сборке. Публикация релиза в GitHub выполняется отдельно.

## Первый запуск и настройки

При отсутствии `~/.config/haproxy-bridge/config.toml` открывается мастер с обычными полями и разделами. Измените пути, Docker/Native, backup, способ Apply и health checks. Ctrl+←/→ переключают разделы, Tab или ↑/↓ — поля, пробел меняет переключатель. Ctrl+S сохраняет, Esc отменяет. Для root используется домашний каталог root. Параметр `--settings /path/config.toml` позволяет использовать отдельный профиль.

Пример всех полей — [config.example.toml](config.example.toml). Их также можно редактировать через O → Настройки. TOML хранится на диске, но вводить его в интерфейсе не нужно. Если файл HAProxy отсутствует, C предлагает явное создание минимального TCP-конфига; существующий файл не заменяется шаблоном.

Основные разделы: `general` — пути и retention; `haproxy` — режим и timeout validator; `docker` — container, compose и service; `native` — бинарник и service; `network` — bind, порты, timeout и SNI; `healthcheck` — параметры проверок; `monitoring` — Unix socket; `ui` — refresh и параметры отображения. Критические подтверждения, валидация и backups не отключаются даже при выключении соответствующих необязательных флагов: безопасность имеет приоритет.

Для отображения интерфейса root не нужен. Для записи нужны права на конфиг, его каталог (атомарная замена), каталог backups и ресурсы validator. Docker требует доступа к daemon, Native Apply — разрешения на `systemctl restart`. Приложение не повышает права автоматически.

## Маршруты и серверы

A открывает новый маршрут и предлагает первый порт, который свободен в конфигурации, начиная с `default_start_port`. C открывает черновик на основании выбранного маршрута. Копия получает собственные имена frontend/backend, исходные параметры и серверы в исходном порядке. Если порт занят, редактор проверяет `порт + 1` и следующие порты до первого свободного, учитывая `frontend` и `listen`. Если вручную ввести занятый порт, `Ctrl+S` покажет предложение, а F3 подставит его.

Редактор маршрута и карточка сервера открываются в режиме навигации. ↑/↓ выбирают строку, Enter начинает ввод. В режиме ввода Enter принимает значение, Esc возвращает прежнее значение. В режиме навигации Q или Esc возвращает на уровень выше.

В редакторе маршрута Tab переключает разделы «Маршрут» и «Серверы». В списке серверов A добавляет сервер, Enter открывает карточку, D запрашивает подтверждение удаления, Ctrl+↑/↓ меняют порядок. В карточке сервера S переносит изменения в черновик. В редакторе маршрута S открывает общий diff. Ctrl+S доступна как альтернативная клавиша.

Адрес и порт сервера вводятся в разные поля. IPv6 указывается без скобок, например `2001:db8::1`. Для нового сервера порт подставляется из `default_target_port`. Роль, health check и состояние выбираются пробелом. `-` в полях вес/интервал/fall/rise сохраняет наследование. Изменения сервера остаются в черновике до подтверждения общего diff, а в файл записываются через Save.

Enter открывает редактор выбранного маршрута. После предпросмотра Esc возвращает к форме с введёнными данными. Адресные метки и роль основной/резервный — разные понятия. Диапазон 100.64.0.0/10 не считается автоматически NetBird.

Порядок backups определяет приоритет **новых** соединений при одном primary и отсутствии `option allbackups`. При нескольких primary действует балансировка; с `allbackups` резервы тоже балансируются. Существующие TCP-сессии автоматически не мигрируют. Подробнее: [HAProxy 3.2 Configuration Manual](https://docs.haproxy.org/3.2/configuration.html).

Перед изменением показывается diff. Смена порта может нарушить работу внешних приложений; менеджер не меняет их конфигурацию. Удаление frontend сохраняет backend, чтобы не разрушить ссылки других frontend. Идентификатор `lv1` автоматически не переименовывается.

Конфигурации с `default-server`, `server-template`, quoted/escaped параметрами или условными блоками доступны для чтения, но их редактирование блокируется до реализации безопасной модели наследования. Парсер сохраняет исходные строки, комментарии и неизвестные директивы при чтении и сохранении без изменений. Неоднозначные конструкции блокируются. Полного редактора произвольного синтаксиса HAProxy нет: неподдерживаемые сложные ACL, шаблоны серверов и многоконфиговые запуски требуют ручной работы и проверки.

## Save, Apply и Docker

Save проверяет внутреннюю модель и реальный кандидат командой HAProxy `-c`, создаёт backup, контролирует хеш исходника и записывает через временный файл с fsync/rename. Права и владелец сохраняются. При внешнем изменении запись блокируется; R перечитывает файл.

В Docker используется immutable image ID работающего контейнера, его mounts, user, workdir и environment. Кандидат подставляется вместо управляемого файла. Неизвестные entrypoint, параметры запуска и неподдерживаемые mounts блокируют validator. Он не гарантирует возможность bind и доступность сети — это проверяется отдельно после Apply.

**Single-file bind mount:** атомарная замена файла на хосте оставляет контейнеру старый inode. Поэтому `restart` для такого mount блокируется. Используйте `recreate` с указанным Compose-файлом и service; другие сервисы команда `up -d --no-deps --force-recreate SERVICE` не пересоздаёт. Compose-файл приложение не изменяет. Предпочтительно монтировать каталог конфигурации; рекомендации и ограничение описаны в [официальном Docker HAProxy](https://github.com/docker-library/docs/blob/master/haproxy/content.md) и [Moby issue 6011](https://github.com/moby/moby/issues/6011).

Apply всегда валидирует сохранённый файл и создаёт точку восстановления. Restart/recreate могут оборвать TCP-соединения. После запуска проверяются running, видимое содержимое config и TCP frontend. Это локальные проверки; при отдельном container network namespace адреса frontend должны быть доступны с хоста, иначе Apply сообщит о неуспешной проверке.

`manual` сохраняет без автоматического применения и явно сообщает, что конфигурация не применена. `graceful` в Docker разрешается только когда PID 1 проверен как HAProxy с `-W`/`-Ws`, файл виден в актуальной версии и после сигнала USR2 подтверждено появление нового worker. При неизвестном entrypoint, отсутствии `/proc`/`docker top` или неподтверждённом master-worker операция блокируется. Долгоживущие соединения обслуживает старый worker в пределах настроек HAProxy (`hard-stop-after` может их ограничить). Docker restart не называется бесшовным reload. В Native поддержан restart systemd-service: перед операцией `systemctl show ExecStart` должен подтвердить прямой запуск выбранного HAProxy с единственным `-f`, указывающим на управляемый файл. Shell-wrapper, переменные и несколько входных конфигов блокируются.

Автоматический rollback выполняется только к точке, созданной после успешного Apply в текущем сеансе. До первого успешного Apply менеджер не объявляет старый файл подтверждённо рабочим. При сбое без такой точки остаются backups и явная диагностика; восстановление выполняется через B и повторный Apply.

## Backups и восстановление

M создаёт backup вручную. B показывает время/ID, размер, SHA-256 и флаги pinned/good. Выбор → Enter/R показывает diff и запрашивает подтверждение Restore. Restore проверяет checksum и HAProxy validator, создаёт backup текущего файла, затем атомарно записывает выбранную версию. Apply выполняется отдельно.

Ротация ограничивает обычные копии настройкой `max_backups`; pinned/good сохраняются. Архив содержит исходный config и метаданные, а не внешние сертификаты/ключи. Если секрет находится непосредственно в исходном config, он также попадёт в backup; каталог должен быть закрыт от посторонних.

## Мониторинг, диагностика и журнал

Runtime API необязателен. Укажите доступный локальный Unix socket HAProxy. Главный экран показывает состояние backend и время с последнего перехода `UP` ↔ `DOWN`. Метка `UP · резерв` означает, что HAProxy видит доступные резервные серверы при отсутствии доступных основных. Строка «Обслуживают» показывает серверы, на которых сейчас есть сессии.

Детали маршрута содержат роли и статусы серверов, время последнего перехода состояния, текущие и суммарные сессии, ошибки подключения, результат и длительность последнего health check и его диагностическое сообщение. `PgUp` / `PgDn` прокручивают детали прямо в списке, `I` открывает их отдельным экраном. «Простой backend» берётся из счётчика HAProxy и относится ко всему backend.

TCP измеряет время установки TCP-соединения, а не ICMP ping. TLS использует SNI из Settings, показывает версию и данные сертификата. При ошибке доверия возможен отдельный диагностический handshake без проверки, но `CertificateValid` остаётся false и ошибка сохраняется; прикладной трафик не отправляется. TCP/TLS-доступность не подтверждает авторизацию VLESS+REALITY.

Журнал действий расположен рядом с файлом настроек: `actions.log`, права 0600. Содержимое конфигов и окружение контейнера в него не записываются. L открывает журнал. Полные ошибки validator доступны в прокручиваемом окне.

## Тесты и ограничения выпуска

```sh
make test
# Только при явно разрешённой работе с тестовым Docker:
make integration
```

Unit-тесты используют временные файлы и mock исполнителя Docker-команд. Integration-тест требует `HAPROXY_BRIDGE_INTEGRATION=1`, запускает изолированный `haproxy:3.2`, проверяет валидный/невалидный config и single-file inode. Он не использует продуктивные пути или контейнер `haproxy`. Самостоятельно не запускайте integration-команду на продуктивном daemon без понимания её действий.

Остаются ограничения: graceful Native пока недоступен; Docker graceful проверен mock- и реальным integration-тестом; сложные схемы импортированной конфигурации могут быть доступны только для просмотра; не все параметры HAProxy представлены отдельными полями TUI. На macOS unit-тесты и сборка не заменяют приёмку Linux/SSH и реального HAProxy 3.2. Инварианты описаны в [docs/SAFETY.md](docs/SAFETY.md).

## Удаление

Удалите установленный бинарник и при необходимости каталог `~/.config/haproxy-bridge`. Каталог backups и исходный HAProxy config удаляются только по отдельному осознанному решению администратора. Удаление приложения не требует менять HAProxy, Compose, Remnawave или NetBird.
